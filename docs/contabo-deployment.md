# Развёртывание Velora на Contabo

Состояние на 19 октября 2026 года. Это рабочий план переноса; действия с сервером
начинаются после покупки VPS и получения точного доменного имени.

## Выбор сервера

- Рекомендуемый старт: **Contabo Cloud VPS 6**, 6 общих vCPU, 12 ГБ RAM,
  100 ГБ NVMe (или 200 ГБ SSD), регион EU/Germany. AI-модели вызываются по API;
  локальный GPU приложению не нужен. Cloud VPS 4 с 8 ГБ RAM допустим для
  демонстрации, но оставляет меньше запаса для MySQL и BI-импорта.
- Contabo предоставляет VPS без администрирования приложения: установку ОС,
  безопасность, обновления, MySQL, резервные копии и саму Velora обслуживаем мы.
- Для первого месяца выбрать помесячный срок и проверить итоговую сумму в
  корзине. Публичная цена «в месяц» у Contabo относится к эффективной цене
  24-месячного срока. Регион вне ЕС и Auto Backup могут добавить плату.
- На публичной странице США Cloud VPS 6 показан от **$6/мес.** при сроке 24
  месяца. По официальному курсу 19.10.2026 (1 USD = 9,2395 TJS) это около
  **55 сомони/мес.** в пересчёте, а не подтверждённая цена месячной покупки.
  Около 70 сомони возможно для месячного тарифа, но итог нужно увидеть в
  корзине для аккаунта в Таджикистане.
- ОС: **Ubuntu 26.04 LTS**, если этот стандартный образ показан при заказе:
  его репозитории содержат PHP 8.5 и MySQL 8.4. Если Contabo предлагает только
  Ubuntu 24.04, не устанавливать приложение с его штатным PHP 8.3: текущий
  `composer.lock` требует PHP >= 8.4.1. Для 24.04 потребуется отдельная
  конфигурация PHP 8.5, которую надо подготовить до переноса.
- HTTPS-сертификат можно выпустить бесплатно через Let's Encrypt. Домен от
  Startcoding может избавить от отдельной покупки домена, если дадут
  поддомен и доступ к его DNS. Расходы на API моделей, почтовый сервис и
  дополнительное резервное хранилище не входят в стоимость VPS.

Источники: [тарифы Contabo](https://contabo.com/en-us/vps/),
[регионы и типы VPS](https://docs.contabo.com/docs/servers-hosting/vps/),
[образы Contabo](https://docs.contabo.com/docs/servers-hosting/images/),
[курс НБТ](https://www.nbt.tj/en/?c=7&id=7),
[PHP 8.5 в Ubuntu 26.04](https://packages.ubuntu.com/php8.5-mysql),
[MySQL 8.4 в Ubuntu 26.04](https://packages.ubuntu.com/resolute/mysql-server).

## Что нужно до переноса

1. Точный домен или поддомен, который Startcoding разрешит направить A-записью
   на IP нового VPS. Нужен доступ человека, который управляет DNS.
2. VPS, созданный с SSH-ключом. Пароль root и закрытый SSH-ключ не передавать
   через чат. Доступ можно выдать отдельному пользователю с ограниченным сроком.
3. Доступная исходная MySQL и возможность сделать консистентный дамп. На момент
   этой проверки соединение с текущей MySQL из рабочей среды не устанавливается.
4. Копии `storage/app/private`, `storage/app/public` и, если используются,
   `instagram_service/instagram_sessions`. Git не содержит эти данные.
5. Текущий `APP_KEY`, если переносим существующую БД: в ней хранятся
   зашифрованные данные каналов. Новый ключ лишит приложение возможности их
   расшифровать. Ключ переносить только защищённым способом.
6. Рабочий SMTP/почтовый сервис для восстановления пароля и приглашений.
   `.env.example` сейчас использует `MAIL_MAILER=log`, что не доставляет письма.
   Старый Google OAuth-клиент для входа не нужен: его кнопки убраны, а секрет
   ранее был опубликован в переписке, поэтому его не следует переносить в
   production `.env`.

## Порядок установки

1. Снять исходный дамп MySQL с `--single-transaction`, включая все таблицы
   `bi_ds_*`, и сохранить отдельную копию до любых миграций. Сверить список и
   число ключевых строк после импорта. Не запускать `migrate:fresh` на данных.
2. Зафиксировать точную версию исходного кода для релиза: текущие локальные
   изменения в рабочем дереве не попадут на VPS при обычном `git clone`.
   Отделить нужные изменения от посторонних временных файлов.
3. На VPS установить обновления ОС, пользователя для приложения, Nginx,
   PHP 8.5 CLI/FPM с расширениями `bcmath`, `curl`, `gd`, `intl`, `mbstring`,
   `pdo_mysql`, `xml`, `zip`, MySQL 8.4, Python 3/venv, Composer и Node.js.
   Оставить MySQL и Instagram-сервис доступными только локально; извне открыть
   лишь SSH, HTTP и HTTPS. Настроить SSH по ключу и фаервол.
4. Разместить код и зависимости: `composer install --no-dev`, `npm ci`,
   `npm run build`. В `.env` задать `APP_ENV=production`, `APP_DEBUG=false`,
   `APP_URL=https://<домен>`, настройки MySQL, SMTP, API и канала Instagram.
   Для двух очередей поставить `DB_QUEUE_RETRY_AFTER=1200`, больше 960 секунд
   лимита долгой ingest-задачи. Не копировать весь локальный `.env` без проверки.
5. Импортировать БД, затем выполнить только новые миграции `php artisan
   migrate --force`. Перенести загруженные файлы и Instagram-сессии, выставить
   права записи для `storage` и `bootstrap/cache`, сделать `storage:link` и
   `php artisan optimize`.
6. Настроить Nginx с корнем `<проект>/public`, PHP-FPM, HTTPS и лимитом тела
   запроса свыше 100 МБ (BI принимает файлы до 100 МБ). В PHP также поднять
   `upload_max_filesize` и `post_max_size` выше 100 МБ. Для Instagram нужен
   отдельный **локальный** HTTP-вход `127.0.0.1:8000`: `/internal/instagram/*`
   намеренно отвергает внешние IP. Instagram слушает `127.0.0.1:8001` и
   отправляет сообщения в локальный вход Laravel. Шаблон Nginx:
   `deploy/contabo/nginx.velora.conf.example`.
7. Запустить `php artisan queue:supervise` и Instagram-сервис под systemd.
   Первый сам поддерживает отдельные очереди `default` и `ingest`. Добавить
   ежеминутный cron для `php artisan schedule:run`; без него ночные бэкапы не
   исполняются. `queue:supervise` сам проверяет зависшие задачи. Шаблоны
   unit-файлов находятся в `deploy/contabo/`.
8. После назначения DNS и TLS обновить публичные webhook URL для подключённых
   каналов и проверить входящие/исходящие сообщения. Старые URL ngrok не должны
   остаться в настройках провайдеров.
9. Проверить `/up`, вход/регистрацию на ru/tg/en, отправку писем, очередь,
   загрузку BI-файла, Telegram и прочие реально используемые каналы. Сделать
   и **восстановить** тестовую резервную копию до открытия доступа пользователям.

## Резервные копии

Текущий `backup:run --only-db` сохраняет дамп **на том же сервере** и не
захватывает загруженные файлы. Это недостаточно после переноса: потеря VPS
уничтожит и данные, и локальную копию. Нужна отдельная копия БД и файлов на
другом хранилище с проверкой восстановления. Contabo Auto Backup можно
использовать как дополнительную ежедневную копию, но итоговая цена видна в
корзине: [описание Auto Backup](https://help.contabo.com/en/support/solutions/articles/103000331723-what-is-the-auto-backup-add-on-and-how-do-i-order-it-).

## Текущие препятствия

- VPS ещё не куплен; точная цена первого месяца и доступность Ubuntu 26.04
  определяются в корзине Contabo.
- Точный домен/поддомен и право менять его DNS пока не подтверждены.
- Исходная MySQL сейчас недоступна из рабочей среды, поэтому дамп и реальный
  объём данных ещё не проверены. Перенос БД нельзя объявить завершённым без
  дампа и контрольного восстановления.
