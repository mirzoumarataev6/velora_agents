## Section D — UNPROVEN SUSPICIONS

- **U-01 — possible stale-snapshot read in `Task::assertColumnHasRoom()`.** The occupancy count (`static::where('project_column_id', $column->id)->whereNull('archived_at')->count()`, `app/Models/Task.php:107-111`) is a plain consistent read, not `lockForUpdate()`. It runs after a locking read on the column (line 94) within the same transaction. MySQL InnoDB's REPEATABLE READ establishes a transaction's consistent-read snapshot at its **first consistent (non-locking) read**, and locking reads are documented to always see latest-committed data regardless of snapshot timing — so if the column lock (a locking read) is genuinely the first query of the transaction, the count's own freshly-taken snapshot should see any transaction it was blocked behind. But at least one call path — CRM task creation with `new_customer_name` set (`Crm\TaskController::store()`) — runs `Customer::forceCreate()` (which itself may issue an earlier plain SELECT, e.g. via `CrmWorkspace::defaultFor()`) **before** `Task`'s own `creating` hook and its column lock. If that earlier read establishes the transaction's consistent-read snapshot, the later occupancy count could read it, undercounting concurrent occupants added by other transactions that committed in between. I could not construct a deterministic proof for this without two genuinely concurrent MySQL connections (SQLite's MVCC model does not reproduce InnoDB's snapshot timing, and the test suite is sqlite-only per `phpunit.xml`), which is outside what this read-only audit's allowed proof methods (failing test / tinker repro / exact code+input) can establish with confidence. Flagged, not claimed.
- **U-02 — scope of the back()-404 pattern (H1) beyond Projects boards.** `ProjectAccess::authorize()`'s `abort_unless(activeTeamId() === board->team_id, 404)` was confirmed as the concrete trigger for Projects. Whether CRM deal/customer detail views, BI dashboard views, or conversation detail views share the identical "hard 404 if active team ≠ resource team" pattern (which would make the `TeamSwitchController` back()-404 failure general, not Projects-specific) was not individually re-traced for every such controller in this session — only Projects was read in full for this purpose.
